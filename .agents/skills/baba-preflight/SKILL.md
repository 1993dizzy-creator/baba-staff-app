# baba-preflight

기준 정책: `docs/agents/baba-agent-workflow.md` §3 (우선순위는 사용자 지시 > `AGENTS.md` 운영 DB·Migration 규칙 > 기준 정책).

## 언제

- 새 작업을 받았을 때, 코드나 문서를 수정하기 **전**에 실행한다.
- 작업 범위가 바뀌었을 때 다시 실행한다. 수정 예정 파일이 추가된 경우가 해당한다.

## 절차

1. 작업 요청에서 수정 예정 파일·디렉터리를 정리한다. 모르면 먼저 읽기 전용으로 코드를 조사해 후보를 정한다.
2. 저장소 루트에서 실행한다.

   ```
   node scripts/agent/baba-preflight.mjs --task "<작업명>" --agent <claude|codex> --files "<경로,glob>" [--apis "/api/..."] [--tables "<table>"]
   ```

   - `--agent`에는 자기 자신을 적는다. Codex는 `codex`, Claude Code는 `claude`다.
   - 기계 판독이 필요하면 `--json`을 붙인다. 종료 코드 2는 차단을 뜻한다.
3. 결과를 해석한다.
   - **불가 / BLOCKED**: 작업을 시작하지 않는다. 「차단 사유」를 그대로 사용자에게 보고한다. 예: 다른 에이전트의 Worktree, `main` 브랜치, 기존 Migration 수정, Migration 버전 중복.
   - **조건부 가능**: 「선행 조건」을 처리하거나 사용자에게 보고한다.
     - 대기 브랜치에서의 작업 준비는 `baba-start`에 맡긴다. 최신 로컬 `main`을 기준으로 생성하며, 이 읽기 전용 Skill 자체는 브랜치를 만들거나 전환하지 않는다.
     - 다른 Worktree가 같은 파일을 미커밋 수정 중이면 사용자 확인 전까지 그 파일을 수정하지 않는다.
     - 공통 파일, 운영 DB·cron 경로, 확정 정책 영역이 포함되면 영향 범위를 보고하고 진행한다. 정책 의미를 바꾸는 경우에는 승인 후 진행한다.
   - **가능**: 진행한다.
4. 사용자에게 요약한다: 판정, 위험도, 수정 예정 파일·API·테이블, 관련 테스트, 확정 정책 영역, 운영 데이터 변경 가능성, 선행 조건.

## 금지

- preflight 결과를 근거로 fetch 외의 원격 작업(push, PR, 병합)을 하지 않는다.
- 차단을 우회하려고 브랜치·Worktree·Migration 이력을 조작하지 않는다.
- `.env.local`의 값을 읽거나 출력하지 않는다. 존재 여부만 확인한다.
