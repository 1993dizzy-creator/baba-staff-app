## 최종 판정: PARTIAL

코드/fixture 안전성 검증은 PASS이나, 실제 현재 진행 주문이 관측되지 않아 **운영 점유 E2E는 미검증**이다. 전체 운영 E2E PASS로 해석하지 않는다.

기준 커밋: `ff59ef2b6895c0c9855716aa24c61e47faf6d75b`.
브랜치: `codex/shared-tables-overview-20261113`.
이번 작업의 운영 DB 조회·CUKCUK 요청은 0회다. 제공된 운영 DB 점검 결과와 기존 카탈로그 실증 자료를 재사용했다. 원본 main, Cron, RPC, DB, 매출/영수증/장부/재고 및 운영 플래그는 변경하지 않았다.

## 재사용한 실제 관측과 한계

Owner가 제공한 2026-11-13 01:30:54(Asia/Ho_Chi_Minh) 점검: 영업일 2026-11-12, 주문 20건 전부 Status 4, Status 1/3은 0건. 마지막 정상 수집 01:27:19, 마지막 오류 없음, 연속 실패 0회. 이때 진행 주문 E2E는 확인할 수 없었고 27개 좌석이 비었다는 뜻도 아니다.

2026-11-10 과거 스냅샷의 진행 상태 주문 8건은 1/2/4/11/16/18/BAR4/BAR6이고 메뉴 상세도 모두 저장되어 있었다. 27개 카탈로그와 이름이 일치한다. 현재 DB에서 동일 OrderId의 결제완료 영수증을 확인한 것은 7건이며 BAR6의 1건은 미확인이다. 이 사실은 당시/현재 BAR6의 점유 또는 미결제를 입증하지 않는다.

`tests/fixtures/tables-observed-shape.mjs`는 이 **제공된 관측 요약을 구조적으로 재구성한 fixture**다. 원본 DB 행의 복사본이 아니다. 원본 OrderId·영수증 ID는 일관된 익명 ID로 치환한 관계를 사용하며, 정확한 Status 1/3 배분·메뉴명·수량·금액·주문 시각은 합성 값이다. 고객/직원 정보·자격 증명은 없다. 과거 날짜를 유지한 제외 검증과, 날짜/시각을 명시적으로 주입한 모의 현재 영업일 검증을 구분한다. 모의 BAR6 사용 중 결과를 실제 점유 관측으로 보고하지 않는다.

## 기존 구현이 정확한 항목

- `table-overview-server.ts`는 기존 매장 설정의 `resolveConfiguredBusinessDate()`로 현재 영업일을 결정하고, 기존 중앙 읽기 RPC에 그 날짜를 전달한다. 영수증 증거도 현재/다음 영업일 범위로 제한한다.
- `table-overview.ts`는 `classifyOrdersForBusinessDate()` 결과의 유효한 open OrderId를 재사용한다. 원본 Status 1/3만 보고 무조건 초록을 만들지 않는다. 결제완료 영수증, 취소 영수증 충돌, 복수 영수증, 상세 부재가 있는 주문을 분리한다.
- 현재 영업일이 아닌 주문은 표시 후보에서 제외된다. 03:00 이후 전날 주문이 다시 점유로 살아나지 않는다.
- 실제 카탈로그의 BAR4/BAR6 및 1·2층 이름은 유일한 정확한 이름으로 매칭되고 원본 MapObjectID를 유지한다. 복합명/단독 BAR/누락/중복/불일치는 임의 분할·배분하지 않는다.
- 같은 주문번호의 서로 다른 OrderId는 별개이며 동일 OrderId의 일치한 중복만 축약한다. 새로운 매출 합계나 금액 배분은 만들지 않는다.
- 실패/지연/incomplete/READ 비활성, 오래된 개별 관측은 정상 점유로 표시하지 않는다.
- 20개 Status 4 또는 진행 주문 0건만으로 빈자리·파랑·보라를 만들지 않는다. 해당 상태/집계는 계속 비활성이며 나머지는 미확인 타일이다.
- `open-orders-read-server.ts`, 공통 중앙 분류기, API의 서명 세션·활성 사용자 검사는 그대로 유지한다.

## 발견된 결함과 최소 수정

**결함: 완료된 이전 주문이 동일 테이블의 유효한 새 진행 주문 표시까지 차단하는 점유 누락.** 초록 오탐이 아닌 false negative다.

재현은 운영 주문 생성이 아닌 두 개의 합성 현재 영업일 주문으로 수행했다.

| 입력/판정 | 수정 전 | 수정 후 |
|---|---|---|
| BAR4의 paid-previous: Status 1 + 유효한 결제완료 영수증 | 공통 분류 converted 1 | 동일 |
| BAR4의 valid-current: Status 1 + 상세 + 최신 관측 + 완료 영수증 없음 | 공통 분류 open 1 | 동일 |
| BAR4 타일 | unknown (누락) | occupied (유효 주문 1개 근거) |
| paid-previous만 있는 타일 | unknown | unknown 유지 |
| 유효 주문 + 상태 불명확 주문 | unknown | unknown 유지 |

기존 `matches.every(verifiedOpen)`은 영수증으로 완료 처리된 이전 주문까지 점유 후보로 보았다. `/tables` 순수 판정부에서 **동일 공통 분류기**로 확인한 converted OrderId만 후보에서 제외했다. 상세 이력·원본 주문·금액은 보존한다. paid-only가 초록이 되거나 불명확한 주문이 무시되는 변경은 없다. 중앙 분류기 자체, 수집기, API/RPC/DB/계산 정책은 수정하지 않았다.

## 남은 조건

실제 영업 중 정상 중앙 스냅샷에 진행 주문이 자연스럽게 관측될 때, 기존 화면/API·OrderId·영수증 연결·테이블명을 제한된 읽기로 대조해야 한다. BAR4/BAR6 및 층별 실제 연결, 동일 테이블 재사용 시 이전 완료 주문과의 공존, 현재 좌석과 초록 표시 일치를 확인한다. 주문 생성/결제/POS 조작이나 반복 감시는 하지 않는다.

빈자리는 Offline 현장 대조 전, 파랑은 현재 테이블 결제완료 근거 확인 전, 보라는 예약 데이터 확보 전 비활성으로 유지한다. 코드 병합·배포·플래그 활성화는 각각 승인 범위 내에서 별도로 진행한다. 이번 PARTIAL은 코드 검사 실패나 작업 차단이 아니라 **실제 현재 진행 주문 E2E 관측 부재**를 뜻한다.
