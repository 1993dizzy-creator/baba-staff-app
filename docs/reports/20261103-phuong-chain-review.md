# Phương 네 지급 원자적 정정안 — 후보 검토 단계

사용자가 인계한 운영 조회 결과를 근거로 작성했다. 이 작업에서는 운영 DB·Notion·브라우저에 접속하지 않았다. **사용자 승인에 따라 57건 개별 청구 필수 가드를 4개 기간 교차검증 승인으로 대체했다.** 독립 full-row baseline과 actor 승인은 여전히 필요하다. 확인되지 않은 개별 품목을 확인 완료로 기록하지 않는다.

사용자가 #2399의 공급자 9/30 원정산표 미확보를 인지하고, 9/16~30 APP 16건 합계와 10/03 실제 지급금이 각각 18,504,000₫으로 일치함을 근거로 1회 증빙 예외를 명시적으로 승인했다. `missingOriginalApproved=true`와 `exceptionApprovalReference=user-conversation:phuong-2399-20261003-18504000-one-time-evidence-exception`에 반영했다. 이 참조는 이번 대화의 사용자 승인을 식별하기 위한 로컬 표기이며 Notion 원문 문서나 운영 실행 승인 번호를 뜻하지 않는다. 원문 미확인을 해소했다고 기록하지 않는다.

`approved_periods`에는 사용자 인계로 확보한 정확히 네 지급의 기간, 공급자 상태/근거/금액(미확보는 null), 지급 전표 근거/금액, APP 금액, 미배분 금액, 예외사항과 이번 #2399 승인을 명시적으로 채웠다. 새로 원문을 조회한 것처럼 기록하지 않는다. #1641의 이미 차감한 936,000, #3336의 7개 거래표도 검사한다. 감사에는 `periodApprovals`를 남기며, 사유에 #2399 원정산표·개별 청구 미확인과 승인 근거를 명시한다. 57개 목표 ID·기존 allocation ID·#388·현금·요청 JSON·감사 원본·8월 지문/복구 보호 로직은 유지한다.

### 실행본 초안과 REVIEW 차이

- REVIEW: `scripts/ledger/phuong-chain-20261103-REVIEW-ONLY.sql` — `execution_mode=false`, 마지막 ROLLBACK. baseline/actor는 NULL이므로 현재 상태에서 차단된다.
- 실행본 **초안**: `scripts/ledger/phuong-chain-20261103-EXECUTION-DRAFT.sql` — `execution_mode=true`, 별도 사용자 운영 DB 승인 참조(`execution_authorization_reference`) 필수, 마지막 COMMIT. baseline/actor/운영 승인 참조는 모두 NULL이다. 현재 실행할 수 있는 승인 완료본이 아니다.
- 두 파일의 정정 본문은 모드와 트랜잭션 종료 방식만 다르다. 실행본은 독립 수집·검토한 **최신 운영 full-row baseline**을 채운 뒤 잠근 현재 상태와 정확히 비교한다. 인계된 합계나 이번 로컬 합성 snapshot을 운영 baseline으로 대체하지 않는다.
- 전체 트랜잭션을 오류 시 중단하는 클라이언트에서 한 번에 실행하도록 명시했다. 오류는 트랜잭션을 중단시키며 중간 문장만 따로 실행하거나 자동 재시도하지 않는다. 이는 향후 실행 지침이며 이번에는 운영 SQL을 실행하지 않았다.
- 기존 baseline/원본 ID/거래처 검사의 재실행 차단에 더해, `ledger_month_close_serial` 잠금 안에서 감사 `correctionKey=phuong-chain-20261103-2399-exception-v1`가 이미 있으면 `CHAIN_CORRECTION_ALREADY_APPLIED`로 중단한다. 키와 별도 운영 승인 참조를 새 감사 행에 남긴다. 새 영구 테이블·RPC·검증 엔진은 만들지 않았다.

변경 관련 검증만 실행했다: `node --test --test-name-pattern="2399 approved exception and execution draft" tests/phuong-chain-review.test.mjs` **1/1 PASS**. 합성 PGlite에서 두 파일 정정 본문의 동등성, 실행 승인 누락 차단, 실제로 채운 기간 승인/예외 기록과 감사 사유, REVIEW 롤백, 실행본의 변경·감사 후 오류 시 전체 롤백, 합성 DB COMMIT 및 1회 키 재실행 차단을 확인했다. 운영 접속·SQL 실행은 하지 않았다. 기존 PASS는 변경되지 않은 보호 범위에서 재사용한다.

새 정책 회귀검증만 실행했다: `node --test --test-name-pattern="period policy requires" tests/phuong-chain-review.test.mjs` **1/1 PASS**. 기간 누락/중복, #3582 잔차 소진, #1641 차감 누락, #3336 거래표 건수 오류, #2399 예외 승인/참조 누락을 차단하고 정상 기간 승인 기록과 최종 ROLLBACK을 확인했다. 기존 보호 범위 PASS는 재사용하며 전체 검사는 반복하지 않았다. 운영 시뮬레이션 인계 기준 예상 잔액은 Phương **13,870,000₫**, Carlsberg **46,219,992₫**, #388 미지급 **3,170,000₫**, #3582 미배분 **1,296,000₫**로 변함없다.

합계 57개 `(payment ID, allocation ID)`를 SQL에 고정했다. 현재 집합과 양방향 EXCEPT 비교하므로 하나라도 추가·누락·다른 지급으로 연결되면 `CHAIN_ORIGINAL_ALLOCATION_IDS_DRIFT`로 변경 전에 중단한다. DELETE/UPDATE도 이 허용 집합으로 제한한다. 원본 ID는 독립 full-row baseline 및 감사 before_snapshot에 계속 보존한다. 새 배분은 기존 57개 payable 후보·금액 검사와 기간별 승인이 필요하다.

목표 payable ID는 위 대화에서 마지막으로 명시된 13/16/15/13건 목록을 유지했다. Notion P1 최신 항목과 직접 재대조했다고 주장하지 않는다. 최신 목록이 이 목록과 다르면 승인 입력을 채우지 않고 실제 내용을 대조해야 한다. 날짜·합계 또는 allocation ID 확인만으로 Zalo 품목 검토를 완료 처리하지 않는다. 개별 invoiceReference/lineEvidence는 더 이상 필수 입력이 아니며 임의 생성하지 않는다.

인계된 운영 읽기 전용 시뮬레이션 PASS는 **57건 / 79,824,000₫, 초과배분 0건, Phương 미지급 13,870,000₫, Carlsberg 미지급 46,219,992₫, #388 미지급 3,170,000₫, #3582 미배분 1,296,000₫, 8월 배분 289건 / 46,053,076₫**이다. 이를 사용자 제공 검증 증거로 재사용하며 직접 운영 재조회나 시뮬레이션을 반복하지 않았다. 앞서 산출한 변화량을 역산하면 동일 기준의 정정 전 미지급은 Phương **32,566,000₫**, Carlsberg **26,227,992₫**이다. 역산값은 별도의 운영 조회 결과가 아니다.

직전 allocation ID 반영 단계에서는 원자적 배분 로직·잔여금 처리·잠금 설계를 변경하지 않고 ID 가드를 정적으로 검토했다. 아래 검증 절의 9/9는 그 이전 버전 실행 증거이며 현재 전체 검사 PASS를 뜻하지 않는다.

### #388 확정 오류 수정

사전 조건을 원금 **3,300,000₫**, 상태 `paid`, 배분 정확히 2건(**#119→#1638 130,000₫ / #928→#2399 3,170,000₫**)으로 수정했다. 사후 조건은 #928만 제거하고 #119 전체 원본 행을 보존하며, 원금 **3,300,000₫**, 상태 `partially_paid`, 배분 합계 **130,000₫**, 미지급 **3,170,000₫**이다. 57개 목표·기존 배분 ID 목록·8월 보호 합계·청구 증빙 차단은 유지했다.

`node --test --test-name-pattern="#388 retains allocation 119" tests/phuong-chain-review.test.mjs`: 새 회귀검증 **1/1 PASS**. #388 실제 원금/두 배분을 반영한 fixture에서 검토 직후의 부분 지급 상태·#119 원본 행·#1638 배분과 현금 이동 보존을 확인하고, SQL 끝의 ROLLBACK 후 #928과 원래 paid 상태를 포함한 전체 baseline 복원을 확인했다. 기존 전체 테스트는 재실행하지 않았다. scoped ESLint와 공백 검사도 PASS다.

기존 `phuong-carlsberg-20261103-REVIEW-ONLY.sql`과 과거 보고서·테스트·8월 재구축 SQL은 변경하지 않았다. 이번 `phuong-chain-20261103-REVIEW-ONLY.sql`은 Phase A를 대체할 **선택지**다. 둘을 순서대로 실행하는 안이 아니다. Phase A 실행 후에는 이 파일의 302건 및 #1641 기준값 검사가 실패한다.

발견된 차액 구간은 10/24 HD015517 **936,000 − APP 0 = 936,000**, 10/26 HD015523 **4,794,000 − APP 4,434,000 = 360,000**, 합계 **1,296,000₫**이다. 날짜별 차이가 누락 매입인지 입고일 차이인지는 미확정이다. 원청구의 품목·수량·단가와 인접일 입고 원본을 대조해야 한다. 읽기 전용 증거 SQL은 후보 57개와 기존 배분 전체, 연결 inventory_logs, 10/23~28의 Phương 원매입을 출력한다. 필요하면 해당 invoice 품목의 다른 입고일도 원본에서 추적해야 한다. 이번 SQL은 매입·입고·비용·선급금·상계·payable을 새로 만들지 않는다.

9월 #1641은 이미 **20,928,000 − 미배송 936,000 = 19,992,000**이다. 10월 HD015517의 동일한 936,000이라는 숫자를 이유로 9월 차감을 재사용하거나 재차 공제하지 않는다.

## 잠금·운영 영향 검토

기존 Phase A는 11개 업무 테이블에 SHARE / SHARE ROW EXCLUSIVE를 명시하고, 10개 테이블의 전체 행 문자열 해시를 전후 계산한다. inventory_logs·movements·감사 같은 무관 업무의 쓰기까지 대기할 수 있고, 전체 정렬/문자열 집계가 원장 규모에 따라 커진다. 기존 파일은 보존하되 운영 실행안으로 우선하지 않는다.

새 안은 명시적 `LOCK TABLE`과 전 테이블 해시를 제거했다. 잠금 대상은 관찰된 지급/원매입 전표·payable·기존 배분 행, 관련 movement/요청/계정/입고 원본과 마감 행이다. `ledger_month_close_serial`과 실제 V2의 `ledger-payable-party:<id>` 잠금 이름을 사용하고, V1의 payable 행 잠금과도 충돌하도록 FOR UPDATE를 사용한다. SERIALIZABLE과 FK 부모 행 잠금으로 기존 snapshot 이후 배분 범위가 바뀌는 경우 대기/직렬화 실패로 중단하도록 설계했다. 후보 밖 지급을 강제로 통합하지 않는다.

읽기용의 통상적인 테이블 잠금 및 DML의 통상 잠금은 PostgreSQL에 남는다. 잠근 두 거래처의 지급/관련 원매입 수정과 월마감은 잠시 대기할 수 있다. 일반 MVCC 조회는 계속 가능하다. lock_timeout 3초, statement_timeout 30초이며, 실패 시 자동 재시도하지 않는다. 여러 문장의 전체 트랜잭션 시간에는 별도 상한이 없으므로 검토 중 열린 트랜잭션을 방치해서는 안 된다.

승인 입력을 채운 REVIEW 파일은 롤백하더라도 PostgreSQL 시퀀스의 nextval 소비는 복원되지 않아 ID 공백이 남을 수 있다. 운영에서 무해한 SELECT 검토라고 취급하면 안 된다. 검토 실행은 격리 DB에서 하고, 원본 시퀀스 재설정은 하지 않는다.

8월 보호 집합은 의도적으로 302개 배분 전체를 읽고 원본 ID/금액/지문을 기록한다. 업무 전체 데이터 해시와는 다르다. 소스에 payment 인덱스, payable 인덱스, 전표 business_date 인덱스와 감사 `(entity_type,entity_id,created_at)` 인덱스가 있으나 운영에 실제 존재하는지/쿼리 플랜/처리 시간/동시성은 이번 작업에서 측정하지 않았다. 따라서 **잠금·검사 범위를 구조적으로 줄였으며, 운영 영향 PASS를 선언하지 않는다.** 독립 운영 검토에서 관련 SELECT의 EXPLAIN(ANALYZE 없이), 인덱스와 대기 세션을 확인해야 한다. 새 인덱스·도구·엔진은 만들지 않았다.
