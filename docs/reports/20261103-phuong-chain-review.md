사용자가 인계한 운영 조회 결과를 근거로 작성했다. 이 작업에서는 운영 DB·Notion·브라우저에 접속하지 않았다. **57개 payable의 원청구 품목 검토와 full-row baseline 승인은 여전히 필요하다.** 확인된 기존 allocation ID 범위는 아래 최종 사전검토에 반영했다. 개별 allocation→payable/금액 원본과 Notion 최신 항목의 전문은 이번 인계에 포함되지 않았다.

## 원자성·원본 보존·실행 차단

- 단일 SERIALIZABLE 트랜잭션에서 네 지급의 기존 링크 해제/금액 수정/신규 연결, #1641 거래처 수정, 영향 payable 상태 계산, 통합 감사 행 1개 추가를 모두 처리한다. 어떤 검사라도 실패하면 전체 롤백한다. 기본 승인 baseline·원청구 검토 목록·actor는 NULL이고, 채워도 파일 마지막은 ROLLBACK이다. 운영용 COMMIT 전환과 실행은 별도 DB 승인 대상이다.
- `evidence-READONLY.sql`은 원청구·실제 allocation ID를 독립적으로 수집하기 위한 SELECT 전용 파일이다. 최종 REVIEW 파일의 `DO $chain$` 이전 부분은 전체 승인 baseline과 후보별 원매입을 출력한다. 이를 독립 스냅샷에서 검토하고 baseline을 채워야 하며, 같은 실행 안에서 현재 값을 자동 승인하지 않는다. 57개 원청구 검토 기록도 별도 승인 입력이다.
- 정확히 같은 지급/payable 쌍은 기존 allocation ID·created_at을 유지한다. 같은 쌍의 금액만 바뀌면 같은 ID로 금액을 수정하고 전후 행을 감사에 남긴다. 없어지는 쌍의 활성 배분 행은 삭제되지만 **ID를 포함한 모든 컬럼을 감사 before_snapshot에 보관**한다. ID를 다른 쌍에 재사용하지 않는다. 신규 쌍은 새 ID다. 기존 ID를 모두 활성 테이블에 남겨야 한다는 의미의 보존은 아니며, 복구 가능한 원본·감사 보존이다.
- 통합 감사에는 기존/목표 범위의 전표·원매입·payable·전체 배분·요청 JSON/result·연결 재고·마감 이력·8월 보호 집합과 승인 원청구 참조가 포함된다. 원전표 source_snapshot과 지급요청의 과거 거래처 값은 그대로 두고 감사 정정과 구분한다. 감사 삽입 트리거의 예상 밖 기존 이력 변경도 롤백한다.
- 원매입과 연결 inventory_log 전체 행, 기존 현금 이동·계정·지급 요청/result, 기존 관찰 범위 감사 이력·월마감 이력, 다른 지급 배분은 보존 비교한다. `source_type=inventory_purchase_log`인데 원본 inventory_log를 해석할 수 없으면 차단한다. 직접 연결되지 않은 전체 재고·감사 테이블을 전수 해시하지 않으므로, 승인 baseline의 writeTriggers에 출력되는 트리거 함수와 그 하위 호출의 범위 밖 부수효과도 실행 전에 검토해야 한다. 운영 트리거 전체에 대한 독립 검토는 아직 미완료다.
- 302건·합계, 8·9월 reopened revision 4, 10월 open, #1641 12개 Carlsberg 8월 링크, #388의 단일 3,170,000 링크, #3337/#1638 보호 금액, 네 지급 일자/금액/유형/거래처, 기존 초과배분, 후보 원금·기간·품목 승인, 후보에 대한 외부 지급 연결 등을 검사한다. 예기치 않은 외부 지급은 그 지급까지 자동 재배분하지 않고 차단한다.

## 잠금·운영 영향 검토

기존 Phase A는 11개 업무 테이블에 SHARE / SHARE ROW EXCLUSIVE를 명시하고, 10개 테이블의 전체 행 문자열 해시를 전후 계산한다. inventory_logs·movements·감사 같은 무관 업무의 쓰기까지 대기할 수 있고, 전체 정렬/문자열 집계가 원장 규모에 따라 커진다. 기존 파일은 보존하되 운영 실행안으로 우선하지 않는다.

새 안은 명시적 `LOCK TABLE`과 전 테이블 해시를 제거했다. 잠금 대상은 관찰된 지급/원매입 전표·payable·기존 배분 행, 관련 movement/요청/계정/입고 원본과 마감 행이다. `ledger_month_close_serial`과 실제 V2의 `ledger-payable-party:<id>` 잠금 이름을 사용하고, V1의 payable 행 잠금과도 충돌하도록 FOR UPDATE를 사용한다. SERIALIZABLE과 FK 부모 행 잠금으로 기존 snapshot 이후 배분 범위가 바뀌는 경우 대기/직렬화 실패로 중단하도록 설계했다. 후보 밖 지급을 강제로 통합하지 않는다.

읽기용의 통상적인 테이블 잠금 및 DML의 통상 잠금은 PostgreSQL에 남는다. 잠근 두 거래처의 지급/관련 원매입 수정과 월마감은 잠시 대기할 수 있다. 일반 MVCC 조회는 계속 가능하다. lock_timeout 3초, statement_timeout 30초이며, 실패 시 자동 재시도하지 않는다. 여러 문장의 전체 트랜잭션 시간에는 별도 상한이 없으므로 검토 중 열린 트랜잭션을 방치해서는 안 된다.

승인 입력을 채운 REVIEW 파일은 롤백하더라도 PostgreSQL 시퀀스의 nextval 소비는 복원되지 않아 ID 공백이 남을 수 있다. 운영에서 무해한 SELECT 검토라고 취급하면 안 된다. 검토 실행은 격리 DB에서 하고, 원본 시퀀스 재설정은 하지 않는다.

8월 보호 집합은 의도적으로 302개 배분 전체를 읽고 원본 ID/금액/지문을 기록한다. 업무 전체 데이터 해시와는 다르다. 소스에 payment 인덱스, payable 인덱스, 전표 business_date 인덱스와 감사 `(entity_type,entity_id,created_at)` 인덱스가 있으나 운영에 실제 존재하는지/쿼리 플랜/처리 시간/동시성은 이번 작업에서 측정하지 않았다. 따라서 **잠금·검사 범위를 구조적으로 줄였으며, 운영 영향 PASS를 선언하지 않는다.** 독립 운영 검토에서 관련 SELECT의 EXPLAIN(ANALYZE 없이), 인덱스와 대기 세션을 확인해야 한다. 새 인덱스·도구·엔진은 만들지 않았다.
