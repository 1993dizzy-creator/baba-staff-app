## SQL 안전 계약 및 운영 확인 한계

`scripts/ledger/july-restore-phase4-batch.sql`은 승인용 SQL 템플릿이며 앱 기능/Migration/상설 DB 함수를 추가하지 않는다. 실행기나 자동 승인 경로는 없다.

- 정확히 9개 행·원본키·제출키·324.1M 합계·개별 action canonical SHA·bundle canonical SHA·외부 승인 SHA 검증. 기완료 145행과 교집합 차단.
- native advance request lock → July month lock → 필요한 ledger 쓰기 잠금. lock_timeout 5초, statement_timeout 90초. inventory/POS 테이블 조회·해시·잠금 없음.
- 각 행 전후 경제유형·금액·날짜·계정 movement 검증, 신규 9전표/14 movement/2 adjustment 및 배치 4계정 증감 검증.
- 0 또는 9개 완료 감사만 허용. 동일 배치 재실행은 감사 actionHash·bundleDigest·기존 전표·가불·임대료 링크를 검증하고 새 행 0개. 충돌 키·부분 감사·외부 7월 가불·7월 급여 batch는 차단.
- 기존 ledger·movement·감사·후보·후불·지급배분·카드·마감·계정·임대·오너 원장을 기존 ID 대상으로 MD5 집계하여 보존. 임대 지급 #1의 명시적 링크 필드만 예외. 변경을 허용하지 않는 테이블은 총 건수도 검증.
- 8~10월 실제 snapshot_hash/리비전 일치, 실행 전후 8월 이후 보유금과 전체 카드 잔액 불변. 기존 전표 #4207~#4210/#3~#6/#1190/#3804 및 144개 복원 원본행 보존. 카드정산 차이를 보정하는 action 없음.
- Owner/Master 권한과 `__ACTOR_USER_ID__`, `__OWNER_APPROVAL__` 게이트 유지. 어떤 오류도 단일 트랜잭션 전체 롤백.

이번 보충 조회는 operator GET 방식으로 현재 7월 거래·감사·관련 계약/급여/투자금·마감 메타데이터만 읽었다. 성공 캡처는 **직렬 GET 17회**이다. 첫 큰 조회 요청은 응답 없이 실패했고, 원인 분리를 위한 최소 계정 조회 GET 1회는 200이었다. 총 HTTP 요청 시도 **19회**, 완료 HTTP 응답 **18회**, 운영 쓰기/SQL/RPC 호출 **0회**. 자동 재시도는 없다. 별도 710건 입고/POS 원본 스캔은 없다.

REST에는 pg_proc 조회 수단이 없어 **이번에 운영 함수 원문을 새로 읽지는 못했다.** manual 계약은 3차의 기존 운영 해시 PASS를 재사용했고, advance/rent/rentActor는 현재 Worktree 정의와 로컬 실행을 검증했다. 4개 기대 해시는 번들에 묶었으며 실제 운영 해시가 다르면 배치가 쓰기 전에 차단된다. 별도 `rpc-contract-preflight-READONLY.sql`은 BEGIN READ ONLY 안에서 4개 함수의 정규화 SHA-256을 비교하고 ROLLBACK한다. 실제 적용 담당자가 현행 해시/권한과 준비 데이터를 확인하고 **별도 Owner 승인**을 하기 전에는 운영 실행 가능 판정을 내리지 않는다. 함수 해시를 무조건 교체하거나 검증을 제거하면 안 된다.

## 영향 범위 검증

`tests/july-restore-phase4.test.mjs` 범위 **8개 PASS**. 초기 기능/DB 검증 7개 PASS 후, 경제/SQL 데이터가 바뀌지 않은 상태에서 파일 SHA/CSV 무결성 검사 1개를 추가 검증했다. 적용 완료 renderer 차단 보완은 해당 archive 검사만 다시 검증했다. 전체 회귀·TypeScript·Build·기존 710건/395행 재조사는 실행하지 않았다.

검증은 별도 PGlite 메모리 DB에 기존 fixture의 제약·월마감 guard와 현재 조회 데이터를 적재하여 수행했다. 이전 운영 SQL은 실행하지 않았다. 운영 자격 증명을 테스트에 제공하지 않았다. 기존 7월 header 조회에는 source_snapshot이 없어 기존 원장의 그 필드는 fixture 기본값이며, 이후 월은 보호 메커니즘용 fixture와 관련 실제 임대 지급 데이터를 사용한다. 따라서 로컬 테스트를 운영 DB 실행 증거로 대체하지 않는다. 기존 1~3차 실제 데이터 PASS는 재사용한다.

검증 내용: 250행 및 4계정 보존, 33행 상태 유지, 124칸 영향, 9행 실제 SQL 실행/동일키 재실행 0쓰기, 임대 지급 1건 전환과 총액 불변, 가불 2건과 비손익 처리, 승인/해시/권한/고유키/계정/카테고리 변경 차단, 마지막 행 오류 시 앞선 임대 링크·가불·전표 전체 롤백, 7월 마감 차단, 기존 지급배분 변조 시 전체 롤백, 산출물 raw SHA/CSV·승인 번들 일치, 3차 재생성 차단.

재현 명령은 `JULY_PHASE4_INPUT_DIR`을 Worktree 내부 `.local/july-restore`로 지정하고 `node --experimental-strip-types --test tests/july-restore-phase4.test.mjs`이다. PGlite 의존성은 기존 설치를 사용한다. 입력자료가 없으면 테스트는 명시적으로 skip하며 PASS로 주장하면 안 된다. 최종 커밋 SHA는 Git 이력과 완료 응답으로 식별한다.
