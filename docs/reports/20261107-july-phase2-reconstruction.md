## 다음 SQL의 처리 계약

최종 검토 SQL:

`.local/july-restore/phase2-final-20261107-r2/next-batch-REQUIRES-OWNER-DB-APPROVAL.sql`

- `__ACTOR_USER_ID__`와 `__OWNER_APPROVAL__`을 유지한다. 승인값은 정확한 payload SHA-256과 결합하고, 별도 bundleDigest도 본문과 대조한다. 입력된 행 목록·고유 키·입고 ID 중복·완료 50행 제외·4계정 합계도 검사한다.
- 기존 `ledger_resolve_inventory_candidate_v1(...,'immediate',...)`를 재사용한다. 선택 로그의 후보를 만들고 해당 RPC로 단 한 번 비용·출금을 생성한다. 입고 수정/자동 sync/repair RPC는 호출하지 않는다. 새 후불이나 기존 지급배분도 만들거나 수정하지 않는다.
- `inventory-log:<ID>` 후보를 confirmed로 연결해 같은 원입고의 후속 중복 비용 생성을 막는다. **이번에 생성한 전표만** `july-restore:<원본 key>`로 source_key를 설정한다. 기존 전표의 키는 수정하지 않는다. 원본 key와 bundle/action hash는 복원 감사에도 남긴다.
- 재실행 시 원본 키 감사·전표·후보·스냅샷·금액·분류·지급계정을 모두 대조한 후 변경 없이 반환한다. 부분 불일치나 중복이 있으면 전체 실패한다.
- 하나의 BEGIN/COMMIT이며 예외는 잡아 삼키지 않는다. 마지막 행 오류도 앞선 전표·출금·후보·감사를 전부 롤백한다.
- 기존 모든 원장·감사·후보·후불·카드배분 행은 기존 ID별 MD5 집계로 보존한다. 쓰기 대상이 아닌 표의 신규 행 추가도 count로 차단한다. 마감·현재 8월 이후 4계정·전체 카드 정산대기 잔액을 전후 대조한다.
- POS/입고 전체 테이블 반복 해시나 테이블 쓰기 잠금은 없다. 선택 입고·품목만 row SHARE 잠금/전후 해시를 적용한다. 장부 쓰기는 배치 동안 직렬화하며 lock_timeout 5초, statement_timeout 90초다.
- 경계 Migration `20261105153442`와 저장소 resolver 본문 SHA-256을 검사한다. 운영 함수 본문을 이번 GET으로 추출해 검증한 것은 아니므로, 운영 본문이 다르면 **등록 전에 중단**한다. 계정 active_from을 바꾸거나 월마감 가드를 우회하지 않는다.
