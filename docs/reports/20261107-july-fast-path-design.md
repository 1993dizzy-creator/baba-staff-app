# FAST PATH — 시트 자금장부 우선 복원 설계·읽기 전용 시뮬레이션

> 후속 최소 구현과 격리 DB 검증은 [구조/241행 배치 분리 보고서](20261107-july-fast-path-implementation.md)에 정리했다. 아래는 최초 설계·시뮬레이션 이력이다. 운영 적용은 수행하지 않았다.

**추천: 잔여 241행을 한 번의 자금장부 배치로 수용하고, 경제 분류·원거래 연결은 별도 상태로 진행한다.** 211행은 실제 4계정 이동, 카드매출 30행은 자금 이동 없는 참조다. 기존 154개 원본행을 다시 기표하지 않으면 시뮬레이션에서 **3/124 → 124/124칸**이 일치한다. 현행 SQL만으로 곧바로 실행할 수 있는 방안은 아니며, 아래 최소 DB/코드 변경이 먼저 필요하다. 이번에는 구현·운영 등록이 아닌 설계와 오프라인 시뮬레이션만 수행했다.

## 최소 데이터 모델

현행 `ledger_transactions`의 type CHECK에는 미분류 현금 거래가 없고, 일반 비용·수입은 카테고리/인식 월이 필요하다. `balance_adjustment`, 투자, 카드정산, 후불 지급 등을 임시로 빌려 쓰면 거래 성격을 거짓 확정하게 된다. 따라서 기존 거래유형을 억지로 쓰는 방식은 배제한다. 별도 CSV만 보관하면 APP 시재는 여전히 3/124이고, 별도 자금 테이블을 기존 시재와 UNION하는 방식은 모든 시재 조회/마감 경로를 수정해야 하므로 더 큰 변경이다.

추천하는 최소 범위는 **원본 registry 1개 + 원거래 claim/link 1개, 비손익 거래유형 1개**다. 배치 이력은 기존 감사 로그를 사용해 별도 배치 프레임워크/테이블을 늘리지 않는다. claim/link는 후속 경제 연결 때만 채우며 초기 cash import는 그것이 비어 있어도 가능하다. 아래 명칭은 설계안이며 아직 생성한 객체가 아니다.

| 객체 | 최소 필드·불변식 |
|---|---|
| `ledger_import_rows` | 원본 문서/탭/행의 고유키, 버전·fingerprint, business_date, 4계정 증감, 카드 참조 증감, batch digest, cash_status, economic_status, 기존 전표 ID 배열 또는 신규 cash 전표 ID, 원문 근거. 같은 키·같은 fingerprint는 noop, 변경된 원문은 conflict로 검토. 기존154행도 registry에는 연결만 기록. |
| `ledger_import_source_claims` | source 종류/ID/claim 목적의 UNIQUE, 소유 그룹/원본 anchor, 연결 전표·배분. 한 결제/입고의 경제 인식 소유 그룹은 하나. 여러 원본 행·부분 지급은 같은 그룹에 배분하며 기존 지급배분 제약을 재사용. 단순히 source ID가 같다는 이유로 다대일 연결을 삭제하지 않음. |
| `historical_cash_event` | confirmed 자금 이동 전용 거래유형. category·recognition_month NULL, source_type=`sheet_cash_import`, 고유 source_key/fingerprint, 원본 실제 날짜·각 계정 이동. receipt/reference만 있는 카드30행에는 전표를 만들지 않음. |

cash_status와 economic_status는 독립한다. 자금 기록이 완료되어도 경제 상태는 `unclassified / source_identified / allocation_pending / resolved / blocked`일 수 있다. 이번 자동 수용241행을 모두 경제 확정으로 표시하지 않는다. 기존153행의 비용·매출 인식과 기존 #1190은 그대로 둔다.

## 중복을 막는 핵심 경계

1. **자금 이동은 cash event 또는 기존 연결 전표 한 곳에만 존재한다.** 후속 POS·입고·급여·투자·세금 연결은 registry/claim을 갱신하거나 비현금 경제 인식만 추가한다. 후속 분류 때문에 같은 입출금을 새 movement로 만들거나 상쇄·재기표하지 않는다.
2. 완료된 과거 기간의 미커버 현금 쓰기는 DB guard로 차단한다. 승인된 cash import와 기존 연결을 검증한 별도 resolver만 허용한다. 기존 POS sync·원입고 즉시비용·가불·후불 지급 RPC를 그대로 호출하면 **다시 출금될 수 있으므로** source coverage를 확인해 연결 경로로 보내야 한다. 애플리케이션에만 있는 체크로 대체하지 않는다.
3. 분류/연결 RPC는 전후 4계정 증감 **0**을 강제한다. 이미 비용이 인식된 채무의 지급은 추가 비용0, 급여 가불은 추가 가불/급여 공제0, 기초 투자금에 반영된 투자/회수는 원금 증감0, VAT 납부는 채무/비용 증거가 생길 때까지 분류 보류한다. 과거7행의 계정 활성기간을 바꾸지 않는다. 새 과거 지급배분을 실제로 허용할지는 별도 검증이며 이번 자금 수용이 그 승인을 대신하지 않는다.
4. 자금 오류가 발견되면 일반 비용/매출/조정으로 목표를 맞추지 않는다. 원본 수정 이력과 별도 승인된 cash correction만 허용하고 124칸 검산을 다시 한다.

이 경계 없이 211행만 입력하는 것은 빠른 복원이 아니라 뒤늦은 중복 입출금 위험을 늘린다. 따라서 coverage guard는 최소 구현에 필수이며 차후 선택 기능이 아니다.

## 표준 Preflight → 일괄 등록 → Postflight

배치마다 여러 업무 RPC의 SQL/해시를 다시 조합하는 대신 **버전이 고정된 단일 cash-import 계약**에 입력 manifest만 전달한다. 엔진/스키마가 바뀔 때 계약 재검토, 데이터가 바뀔 때 manifest 재승인이다. 실제 RPC hash 검사를 생략하는 것이 아니며, 변경 시 fail closed는 유지한다.

| 단계 | 공통 처리 | 배치마다 반복하지 않는 일 |
|---|---|---|
| Preflight | 대상 기간·source fingerprint·241키/154기존 링크·278개 leg·0손익·124칸 예상·Owner 권한·한 개 import 엔진 계약 확인. 변경 가능한 소스/대상 키만 fresh 조회. 마감3개/현재4계정/카드·배분의 보호 지표 캡처. 새9행 전표 ID는 키로 찾고 추정하지 않음. | 710입고/전체POS 재조사, 전체DB 반복 해시, 거래별 서로 다른 RPC 정의 추적 |
| 한 번의 등록 | 오너 승인 manifest 하나, temp staging → registry395 연결/보존 → 신규211 cash 전표/278 leg + 참조30 저장. source key·fingerprint 충돌 차단. 동일 source 재실행 noop. 단일 트랜잭션·오류 시 전체 롤백. | 날짜31회/개별241회 승인, 행별 SQL 수제 작성 |
| Postflight | **COMMIT 전** 모든124칸·4계정 기대 이동·source coverage·new row/leg 수·0신규손익·0카드변경·기존 마감/원장 보호를 공통 검사. 보호 위반 시 전체 롤백. 결과 감사 기록과 period cash seal 생성. | 새 보호 SQL·새 검산 보고서 형식 제작 |

새로운 registry/claim은 RLS·권한 제한과 service-role 실행 경로의 Owner/Master 확인이 필요하다. 일반 앱 사용자가 manifest나 승인 상태를 직접 덮어쓸 수 없어야 한다. 운영 자료/인증을 테스트에 제공하지 않는다. 이번에는 운영용 RPC·DDL·Migration·실행 SQL을 만들지 않았다.

표준 도구의 **오프라인 계약**은 `scripts/ledger/cash-first-simulation.mjs`의 `cashPreflight / simulateCashBatch / cashPostflight`로 구성했다. DB 커넥터나 실행기는 없다. 메모리의 staged copy로 재실행·원문충돌·실패 원자성 조건을 실험했을 뿐, 아직 구현하지 않은 PostgreSQL 원자성이 PASS라고 주장하지 않는다.

## 필요한 앱 변경과 승인 횟수

현재 fund 조회는 confirmed movement를 type 제한 없이 읽고, 손익 쿼리는 명시적인 income/expense/sales/expense_recognition만 읽는다. 따라서 신규 cash type은 기존 자금 집계에 들어가고 손익에서는 빠질 수 있다. 다만 다음 작은 변경이 필요하다.

- DB: 신규 type 허용, registry/claim 2개 소형 테이블, 공통 import/coverage guard와 비현금 link 경로. 기존 Migration은 수정하지 않고 추후 별도 승인된 새 Migration으로 적용.
- APP: 내역/상태에 `과거 자금·분류 대기` 표시, 기존 dashboard의 unknown type → `otherFundAdjustment` fallback에서 신규 cash type을 분리한 **미분류 자금** 항목, 후속 resolver에서 covered cash 재생성 차단. 현재 손익 whitelist는 확장하지 않음. 기존 지급완료 표시가 payment movement를 요구하는 곳은 registry의 covered payment를 참조하도록 연결해야 함.
- 전면 UI/장부 재개발·새 품목/급여/투자 모듈·새 거래별 배치 엔진은 필요하지 않다. 분류 대기 수와 cash/economic 완료 여부는 별도 필드로 노출한다.

| 앞으로의 데이터 승인 방식 | 횟수 | 제안 대비 감소 |
|---|---:|---:|
| 날짜별 가정 | 31 | **31→1, 96.8%** |
| 행별 가정(상한 비교) | 241 | **241→1, 99.6%** |
| 기존처럼 9~62행씩 나누는 가정 | 4~27 | **1회로 축소** |
| FAST PATH 자금 데이터 배치 | **1** | 경제 예외의 후속 승인은 별도 |

기존1~4차의 이미 소요된4회 승인을 없애는 것이 아니다. 공통 엔진·스키마를 처음 배포하는 **별도 코드/DB 구조 승인 1단계**도 필요하므로 첫 전환은 ‘구현/구조 승인 + 자금 데이터 승인’ 두 단계다. 이후 월별 데이터는 엔진이 같으면 manifest 하나를 승인한다. 실제 개발시간/운영 실행 초수는 측정하지 않았고, 감소율은 승인·준비 반복 횟수의 구조적 비교다. 미래 경제 예외241건의 증거 확인이 모두 사라진다는 뜻은 아니다.

## 시재 검산 완료와 회계 마감 완료

분리할 수 있다. `cash_reconciled`는 정본 coverage395/395와124칸 일치, `economic_closed`는 비용/수익 귀속·급여/투자/세금·POS/카드 채권 및 정산까지 검증된 상태다. **현금 검산만 끝난 7월을 기존 ledger_month_closures의 완전한 마감으로 저장하면 안 된다.** 미분류 자금241행은 별도 대기 상태로 남기고 결산/마감 RPC는 경제 미해결이 남아 있으면 차단하거나 별도 미완료 표시한다. 기존8~10월 마감 snapshot은 재계산/덮어쓰기하지 않는다.

미해결은 POS·카드174행 + 후불/선지급19행 + 특수·증거 부족48행이다. 다른67행의 거래 규모는755,323,085₫다. 대표 고액은 #184 162.5M 투자/현금교환, #123 151,766,890₫ 6월 급여, #367 111,942,359₫ VAT, #211 35,866,000₫ Phương, #76 34,879,771₫ 전기다. 이들의 **자금 기록은 수용하되 경제 유형/배분은 보류**하므로 정상 자금 처리까지 묶어서 중단하지 않는다. 카드/후불 업무의 기존 차단 사유가 해소됐다는 판정은 하지 않는다.

## 8월 경계와 1~6월 재사용

7월 movement는 기존 `fundMovementInScope`의 8/1 cutover로 현재4계정에 재합산되지 않는다. 7월 기말300,353,642₫과 8/1의4개 기초 전표는 이어지지만, 새7월 movement를 8월 자금에 다시 더하지 않는다. 카드에는 이 business-fund cutoff를 적용하지 않으며, 이번에는 카드 movement 자체를 만들지 않는다. 8~10월 snapshot·8월 이후 원장/지급배분은 읽기 전용 보호 대상이다.

1~6월에는 문서/탭/기간, 계정 매핑, 해당 월 기초/일별 목표, 기처리 고유키만 바꿔 같은 pipeline을 사용할 수 있다. 월마다 새 SQL/RPC를 만들지 않는다. 단, 현재 코드의 hardcoded **8/1 cutoff만으로는 1~6월 전체 뷰 경계가 충분하지 않다.** 7월의 별도 기초600,859,817₫도 있으므로, 각 뷰/계정에서 기준 기초일 이전 복원 movement를 다시 합산하지 않도록 기존 scope를 ‘해당 뷰의 적용 가능한 기초 boundary’로 일반화해야 한다. 첫 월 기초는 독립 근거가 필요하고, 다음 월 기초가 앞 월 기말과 다르면 임의 조정 없이 예외로 남긴다. 1~6월 원본/목표는 이번에 가져오거나 조사하지 않았다.
