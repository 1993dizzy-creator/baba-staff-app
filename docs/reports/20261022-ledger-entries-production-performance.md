# Entries 운영 초기 로딩 실측 — 2026-10-22

## 결론

운영 `/admin/ledger/entries?month=2026-10`에서 6초대 초기 지연을 재현했다. 주요 원인은 공용 장부 API의 서버 대기다. 필수 API의 본문 수신이 끝난 뒤 장부 이력/날짜 헤더가 표시되기까지는 약 23~79ms였다.

Entries 전용 렌더 수정으로 2~3초 목표를 안정적으로 달성할 근거가 없어 제품 소스를 수정하지 않았다. 공용 API·회계 계산·POS는 읽기 전용이라는 작업 범위를 지켰다. 운영에서 2~3초 목표를 달성했다거나 개선을 완료했다고 보고하지 않는다.

## 조건과 측정 방법

- URL: https://baba-staff-app.vercel.app/admin/ledger/entries
- Windows Chrome 156.0.8078.47, 관리자(master) 로그인. 이름·ID·장부 내용은 보고서에 기록하지 않았다.
- PC 1280×900, 모바일 형태 390×844 viewport. 실제 휴대폰 CPU/네트워크 에뮬레이션 또는 throttling은 아니다.
- KO 우선, VI 추가. 10월 첫 진입·새로고침·문서 재진입, 8/9/10월 전환, 이력/날짜 펼침, 지출·급여·전체 필터.
- 사용자가 일반 Windows에서 실행한 별도 Chrome의 CDP `127.0.0.1:9444`에 연결했다. 로그인 정보는 측정 context로 메모리에서만 전달했다. 인증정보나 원문 장부 응답을 파일로 저장하지 않았다.
- 원래 사용자의 탭과 기본 프로필을 변경하거나 종료하지 않았다. 새 측정 context만 사용했다. Git 명령, DB 변경, Migration, 배포는 하지 않았다.
- fetch/XHR의 GET·HEAD 이외 메서드와 form submit을 차단했다. 저장·결제·취소·마감 기능은 실행하지 않았다.
- 첫 진입은 새 context의 문서 탐색, 새로고침은 같은 context에서 reload, 재진입은 `/admin` 방문 후 Entries 문서 탐색이다. SPA의 링크 재진입과 구분한다.
- 첫 표시 시점은 실제 데이터로 생성된 장부 이력/날짜 헤더의 가시성을 확인하고 두 번의 requestAnimationFrame 뒤 기록했다. 로딩 placeholder는 완료로 세지 않았다. 기본 UI는 이력/날짜가 접혀 있어 첫 표시가 모든 개별 거래행의 표시를 의미하지 않는다.
- Resource Timing으로 필수 API의 TTFB·본문 수신 완료·전송/압축 해제 크기를 기록했다. `.json()` 완료 시점은 본문 소비/파싱을 포함하며 순수 JSON.parse 시간으로 보지 않는다.
- 클릭/필터 시간은 Playwright 제어 비용을 포함한다. API 완료→첫 표시 시간은 브라우저 내부 시계를 사용한다.
- 초기 복제 context에 localStorage가 전달되지 않은 준비 시도 2건은 로그인 화면으로 이동해 측정에서 제외했다. 사용자 로그인 세션은 유효했으며 재로그인을 요구하지 않고 계측 context의 상태 전달을 수정했다.

| 단계 | 탐색 시작 후 시점 또는 소요 |
|---|---:|
| 장부 API dispatch | 1.575초 시점 |

| 필수 API 본문 완료→표시 | 73ms |

이 표본에서 `/api/admin/ledger?month=2026-10&scope=entries`의 기존 Server-Timing:

- 전체 서버 처리: 4,686ms.
- 인증: 243ms.
- `base_reads`: 2,509ms.
- `inventory_display`: 1,568ms.
- 두 단계 합계: 서버 전체의 약 87%.
- 이후 브라우저에는 55ms long task 1개가 관찰됐지만 6초 지연을 설명하는 주 비용은 아니다.

기본 조회와 재고 보강 단계에는 Supabase 왕복·대기·후처리가 함께 들어 있다. 각 SQL의 실행시간, pool 대기, 네트워크를 분리 측정한 결과가 아니다. `base_reads` 내부 특정 쿼리나 `inventory_display` 내부 특정 함수를 단독 원인으로 확정하지 않는다.

일반 측정의 장부 API 33개(월 전환 포함)에서 서버 전체 중앙값은 1,153ms, 최대 5,364ms였다. 단계별 중앙값은 auth 44ms, base_reads 447ms, inventory_display 345ms였다. 단계별 중앙값을 합쳐 하나의 실제 요청 시간으로 해석하면 안 된다.

## 요청·payload·렌더·메모리

- 최초 표시까지 보통 GET 6건: session, 휴가 대기 요약, 장부, 마감 상태, 미납, 투자금 요약.
- 장부 요청은 한 번이며 `scope=entries`가 적용되어 있었다. 동일 동작 내부에서 장부 API 중복 요청은 관찰하지 않았다.
- 미납·투자금 조회는 메인 데이터의 적용을 막지 않았다. 마감 상태는 필수 의존성으로 유지돼 있었다.
- 이력/날짜 펼침 및 필터 측정에서 추가 API 요청은 0건이었다.
- 최초 10월 실제 장부: 363건, items 502개. 초기 DOM은 183개였고 펼쳐진 거래행은 없었다. 전체 363개 거래행을 초기 DOM에 생성하는 형태는 아니다.
- 첫 진입의 CDP JS heap 약 5.9~6.4MiB, 관측된 script 전송량 약 313KB. 계측과 framework를 포함한다. 메모리 개선이나 누수 해결을 수행했다는 뜻은 아니다.

|---|---:|---:|---:|
| 2026-08 | 464 | 779,442B | 약 70KB |
| 2026-09 | 457 | 834,470B | 약 82KB |

8월 전환은 관측된 조건에서 약 1.64~1.98초, 9월은 1.62~2.40초, 10월 복귀는 1.37~1.62초였다. 날짜 펼침은 약 55~75ms, 지출/급여/전체 필터는 약 55~62ms였다. 이력 전체 펼침은 약 153~164ms였다. 이 값에는 자동화 클릭/대기 비용이 포함된다.

## 읽기 전용 보조 조회 순서 실험

제품 소스를 바꾸지 않고 측정 context에서만 미납·투자금 요약의 fetch 시작을 메인 장부 본문 완료 뒤로 늦췄다. 비교 순서는 기존→지연→지연→기존→기존→지연이었다. 보조 응답이 완료될 때까지 기다린 후 context를 닫았고, 양쪽 모두 총 GET 6건이었다.

| 조건 | 첫 표시 3개 표본(초) |
|---|---|
| 기존 순서 | 9.40 / 1.66 / 1.88 |
| 보조 조회 지연 | 2.74 / 1.66 / 1.43 |

서버 변동이 매우 크고, 운영 장부행도 363→364건으로 자연 변화했다. 캐시/서버 상태·동일 데이터가 통제되지 않아 인과적인 성능 개선으로 결론내리지 않았다. 9.40→1.43초 개선이라고 비교하지 않는다. 이 실험을 근거로 제품의 조회 순서를 수정하지 않았다.

## 로컬 규모 증가 검사

별도 Production UI 하네스에서 합성 API payload를 미리 준비해 서버 비용과 분리했다. 실제 운영 성능 수치와 섞지 않는다.

| 합성 장부행 | 응답 완료→첫 표시 중앙값 | 날짜 펼침 중앙값 | 펼침 후 DOM |
|---:|---:|---:|---:|
| 120 | 65ms | 62ms | 1,638 |
| 1,020 | 69ms | 228ms | 13,338 |
| 3,020 | 72ms | 572ms | 39,338 |

초기 렌더보다 대량 행 펼침에서 증가 비용이 있었다. 금액 formatter 생성도 3,020건에 약 34ms, formatter 재사용은 약 0.9ms였으나 현재 운영 초기 병목을 해결하는 근거가 아니어서 수정하지 않았다.

## 원인 위치와 작업 범위

- `app/api/admin/ledger/route.ts`: base_reads는 여러 기본/집계/당월 조회의 Promise.all 완료를 포함한다. 개별 요청별 세부 계측이 있어야 느린 조회를 구분할 수 있다.
- 같은 API 약 345행: withInventoryDisplay와 loadInventoryProjectionIssues를 병렬 실행한 뒤 inventory_display를 기록한다.
- `lib/ledger/inventory-display.ts`: 전체 transaction을 200개씩 나눠 candidate overlay를 읽고, inventory log supplier를 다시 읽는다. 반복 batch는 직렬 처리한다. 개별 batch의 운영 시간은 별도 측정하지 않았다.
- `lib/ledger/purchase-case-loader.ts`: 재고 이슈·로그·관련 transaction/audit 및 advisory preview를 읽는다. 무결성/누락 검출 의미가 있어 임의 생략하지 않는다.
- `app/(protected)/admin/ledger/entries/page.tsx`: 메인/마감 상태는 병렬, 보조 데이터는 비차단이며 날짜별 행은 펼칠 때 렌더링한다. 이를 보존했다.

현재 주 병목을 줄이려면 공용 API의 기본 조회 및 재고 보강 구간을 추가 조사해야 한다. 공용 API/회계 helper 수정은 허용되지 않아 여기서 제품 변경을 중단했다. 정확한 쿼리별 시간과 의존관계를 확인하기 전 조회 제거·공용 캐시·스냅샷 생략·DB/Migration 변경을 제안하거나 실행하지 않았다.
