## 적용 이력과 대상 보존

95행은 실제 `phase2-final-20261107-r2/remaining-345-status.csv`의 `needs_link`를 추출하고 기존 JSON과 키를 대조했다. 95행·111,839,142₫이 정확히 재현됐다. 312행 중 나머지 217행은 원문 근거·기존 POS 키 61행을 포함해 그대로 보존했다. #211(Phương 35,866,000₫)은 이 95행에 없으므로 추가하지 않았다. 이번 95행은 전부 기존 원입고 관련 거래이며, POS·카드·급여·투자·VAT 등 다른 경제유형은 실행 대상으로 편입하지 않았다.

## 등록 범위를 넓힌 방법

**계산 합계가 시트 실지급과 같은 33행·57,122,342₫**은 기존 입고 resolver의 `immediate`를 재사용한다. 다수 입고를 한 시트행으로 연결하되, 각 원입고의 실제 금액·기존 카테고리를 유지한다. 따라서 정상 다대일 원본행이 혼합 품목/비용분류라는 이유만으로 막히지 않는다. 금액을 임의 분배하지 않는다.

**계산액과 차이가 있는 29행·6,699,000₫**은 시트 실지급 정본으로 비용·출금 **원본 행당 1건**을 기존 manual RPC로 기록한다. 품목별 청구액을 추정하거나 소액 차이를 별도 비용·조정금으로 생성하지 않는다. 각 원입고의 수량·단가·계산액 및 음수 정정은 그대로 남긴다. #53은 원문과 실제 품목이 모두 과일이므로 해당 묶음 비용은 과일 매입으로 분류하며, 원입고의 기존 분류는 수정하지 않는다.

이 묶음 비용으로 이미 인식한 각 양수 원입고의 독립 후보는 기존 resolver의 `dismiss`를 사용해 **해당 원본 key와 비용 전표 ID를 사유로 명시**한다. 구매 자체가 없었다고 기록하는 것이 아니라, 별도 전표로 중복 인식하지 않을 후보임을 표시한다. 원본 행 감사에는 전체 비용 전표·입고 ID를 연결한다. 동일 snapshot 재동기화는 변경 없이 종료되고, 이후 source 변경은 pending review로 넘어가며 자동 비용·출금이 추가되지 않는 것을 현재 sync 본문을 재현한 로컬 DB로 확인했다.

62개 원본 행은 이 두 경로를 합쳐 **신규 비용 전표/출금 110건**으로 표현된다(원입고별 81건 + 묶음 비용 29건). 합산 비용·출금은 정확히 **63,821,342₫**이다. 신규 source claim은 161개(confirmed 81개, 위 묶음 사유의 dismissed 80개)이며, 음수 정정 로그 2개는 추가 후보·비용으로 만들지 않는다. 기존 후불·배분은 변경하지 않고 새 후불도 만들지 않는다.

## 해결한 연결 문제

- #14·39·47·79·217·279·337·382 등의 여러 입고/비용분류를 원본 행에 묶었다. #352는 기존 메모의 #7979→Cho 1,490,000₫, 나머지 6로그→법인 5,236,000₫을 사용해 분할 수금액을 정확히 대조했다.

## 아직 등록하지 못하는 이유

**연결 완료·등록 제한 7행:** `133,137,210,270,273,332,372`.

원입고와 시트 지급은 식별했지만 비용 발생일과 지급일이 다르다. 현재 계정 5개의 `active_from=2026-08-01`이고 기존 후불 지급 V1(V2 내부 호출)은 지급일에도 이 조건을 검사하므로 7월 지급은 `invalid_account`다. #273 같은 과거 입고 지급을 7월 지급일의 신규 비용으로 바꾸지 않았다. #133·270의 선지급도 기존 선지급 모듈의 계정 기간/적용 여부를 임의 우회하지 않는다. 계정 날짜 변경·새 Migration·RPC 변경 없이 이 7행을 현재 SQL에 넣지 않았다.

**추가 증거 필요 17행:** `8,21,61,81,105,109,124,148,202,214,240,241,261,263,271,349,398`.

사용자 지정 약한 연결 6행은 모두 유지했다. 품목 불일치, 복수 공급자/청구기간, #6217 재기록 의심, 금액·수량/일별 청구배분 불명확이 남는다. 특히 #202/#271의 반대 21,600₫ 차이를 상계해 일별 비용으로 임의 확정하지 않았다. #240의 정정 후 차이·#241/#261/#263의 미확인 지급차도 억지로 등록하지 않는다.

**별도 보류 9행:** `7,19,83,94,164,201,250,251,276`.

도어 클로저·도구·장비/비품 등 비용과 자산/내구 비품의 경제유형을 확정할 증거가 부족하다. 낮은 금액을 근거로 자본화 기준을 새로 만들지 않았다. 반면 품목이 확인된 소모성 포장재·청소 소모품·필터·꽃·세제·장갑 등은 별도 자산으로 추정해 계속 막지 않았다. 정확한 행별 이유와 원문은 근거 CSV에 있다.

## 읽기 보충·RPC·보호 계약

기존 운영자 방식으로 Main의 환경 파일을 프로세스에서만 읽었다. 자격 증명 복사·출력·테스트 제공은 없다. 이번 HTTP는 **직렬 GET 34회**, SQL/RPC/쓰기/POS 호출은 **0회**다. 95행 관련 ID 236개와 새로 연결된 정정 여부, 관련 품목 116개, 후보·전표·지급 중복 및 소수 분류 메타데이터만 읽었다. 710건 전수조사나 POS 재조회는 하지 않았다. 후보/전표 각각 2건은 #85의 #6231과 #228의 #7192로, 이미 적용된 33행 중 다른 행의 **제외 ID**다. 이번 귀속 로그로 다시 쓰지 않았다.

후불은 원비용 business_date를 FK로 필터해 8월 전 기록만 조회했다. Carlsberg #1830(paid)와 9월 지급배분 #1796은 보존하며 #3804와 함께 배치에서 제외한다. 기존 카드정산 69건과 이월 차이 **−6,102,347₫**은 실행 후보에서 계속 제외한다.

resolver 본문은 이전에 사용자가 운영에서 확인한 해시 `edcfb9d5…ed7c4d5`와 일치하는 Migration 패치 재현본을 재사용했다. manual·sync·소스 잠금·economics 본문도 저장소의 실제 후속 패치를 반영해 검증했다. **이번 REST 읽기 경로에서 이 네 함수의 운영 본문을 새로 추출한 것은 아니다.** SQL은 5개 본문의 정규화 SHA-256을 운영 실행 직전 실제 `pg_proc`와 비교하며, 하나라도 다르면 어떤 등록도 하기 전에 중단한다. `rpc-contract-preflight-READONLY.sql`로 별도 무쓰기 비교도 할 수 있다. 운영 함수/권한을 변경하거나 해시 검사를 완화하지 않았다.

SQL은 승인 payload/bundle SHA-256, 정확한 행 목록·원본 고유 키·source 중복·완료 83행/약한 6행 제외를 검사한다. source 전체 잠금을 기존 함수의 순서대로 먼저 잡은 뒤 장부 쓰기를 직렬화한다. 원입고/재고 전체 및 POS 테이블 쓰기 잠금·반복 해시는 없고 선택 source와 품목만 전후 비교한다. timeout은 잠금 5초·statement 90초다.

기존 모든 장부·후보·감사·후불·배분·카드 및 8~10월 마감은 기존 ID별 MD5/행 수로 보호한다. 신규 전표·출금·후보 수, 원본 행의 합계 및 계정별 전후 증감, 8월 이후 자금과 전체 카드 잔액도 검사한다. 하나의 BEGIN/COMMIT이고 오류를 삼키지 않아 실패 시 데이터 전체가 롤백된다. PostgreSQL sequence gap은 정상이며 데이터 롤백과 구분한다.
