## 결론과 범위

기존 데이터를 다시 쓰지 않고 **조회 모델을 통합**했다. DB 구조 변경·Migration·새 지급/조정 RPC가 필요하지 않은 설계를 적용했다. 기존 소액차감 전표와 배분을 그대로 읽어, 원입고에서 원금·조정·인정금액·실제 지급액·미지급액·정산 상태를 함께 확인한다.

## 통합 설계와 구현

### DB

**변경 없음.** 원금·조정·현금 지급을 중복 저장하는 테이블을 추가하지 않는다. 금액이 작다는 이유로 자동 조정을 만들지 않는다. 미확정 16일 이후 거래와 원인 불명 거래를 정산하는 기능도 추가하지 않는다.

기존 배분을 그대로 사용하되, 다음 조건을 모두 만족한 행만 비현금 소액조정으로 분리한다: 확정 비용 차감 전표, 전용 source_type/adjustmentType/source_key, nonCash=true와 cashMovementAmount=0, 원금·조정액의 일치, 원매입/채무 식별자 일치, 실제 자금 이동 없음.

- original_amount = 기존 채무 원금
- adjustment_amount = 검증된 비현금 배분액의 음수 합
- effective_amount = original_amount + adjustment_amount
- cash_paid_amount = 확정 배분에서 검증된 비현금 조정을 제외한 합
- remaining_amount = max(0, effective_amount − cash_paid_amount)

차감 조정 배분은 **인정금액에서 한 번만** 반영한다. 기존 총 배분 전체를 인정금액에서 다시 빼지 않는다. 조정만으로 잔액 0이면 cash_paid_amount=0이어도 paid로 표시한다. 이 계산은 조회용이며 DB 상태 변경을 실행하지 않는다.

금액 합산은 numeric(16,3)에 맞춰 정수 천분 단위 BigInt로 수행하고 응답 때만 Number로 변환한다.

### API

- /api/admin/ledger: 지급 배분 조회에 연결 전표의 종류·부호·스냅샷·자금 이동을 함께 조회한다. 원입고 항목에 purchaseSettlement를 제공하고 그룹 금액은 인정금액 기준으로 합산한다.
- paidExpense는 비현금 조정을 실제 지급액에 섞지 않도록 보정한다. 인식 비용/P&L의 원천 합산은 기존 전표를 그대로 사용한다.
- /api/admin/ledger/payables 및 거래처 상세/과거월 상세: 동일 모델로 실지급액과 정산 내역을 제공한다. 일반 채무 월말 기준과 결제 미확인 현재 처리 큐의 시점 계약은 유지한다.
- 지급 POST / ledger_pay_payables_v1, 권한·행 잠금·월마감·입고 정정 V3는 수정하지 않는다.
- 지급 잠금에 쓰이던 기존 배분 금액은 유지한다. 화면의 실제 지급액은 별도의 명시적 cashPaidAmount/settlementPaidAmount를 사용한다.

### UI

공유 PurchaseSettlementDetails 컴포넌트를 장부 매입 상세와 결제 미확인 목록에 연결했다. 6개 정산 항목과 지급·조정 전표 ID, 조정 사유, source_key 및 원본 source_snapshot을 접힌 감사 영역에서 볼 수 있다. 기존 단가·수량·원입고 이력을 보존한다.

소액조정은 기존 시스템 정정 필터를 유지해 독립된 일반 매입으로 중복 노출하지 않는다. 지급 전표는 현금 감사와 기존 결제 필터를 위해 유지하며, 비용 참여가 없는 transfer 성격도 유지한다.

완료된 조정 매입은 remainingAmount=0으로 결제 미확인 처리 대상에서 제외된다. API의 완료 기록은 감사/호환 목적으로 유지하지만 큐는 양수 잔액만 표시한다.

### 기존 부분지급 재시도 위험 (미해결로 보고)

현재 지급 RPC에는 요청 ID 기반 멱등성 계약이 없다. 잔액이 충분할 때 동일한 1,000₫ 부분지급 요청을 재시도하면 각각 새 지급으로 기록될 수 있음을 격리 DB에서 재현했다. 전액 지급 후의 재시도는 잔액 검증으로 차단된다.

이번 조회 통합은 새 지급 경로를 추가하지 않는다. 이 위험을 고쳤다고 주장하지 않으며 기존 RPC를 변경하지도 않았다. 일반 부분지급의 강한 멱등성까지 보장하려면, 후속 설계에서 요청 키·요청 본문 지문·처리 결과 보관과 DB 유일 제약/잠금, 지급 API·UI의 재시도 키 재사용을 함께 구현해야 한다. 이는 별도 검토와 운영 Migration 승인이 필요한 작업이다.

## 변경 파일

- lib/ledger/payables.ts — 공통 정산 모델, 비현금 검증, 실지급/월별 순매입 분리
- lib/ledger/entries.ts — 원입고 항목 정산 정보 및 인정금액 그룹 합산
- lib/ledger/payment-verification.ts — 동일 모델 기반 실제 지급·잔액·확인 상태
- app/api/admin/ledger/route.ts — 조회 필드 확장, paidExpense 비현금 중복 제거
- app/api/admin/ledger/payables/route.ts — 일반/확인 큐/과거월 정산 일치
- app/api/admin/ledger/payables/[partyId]/route.ts — 거래처 상세 정산 정보
- components/ledger/PurchaseSettlementDetails.tsx 및 .module.css — 공통 6항목·감사 상세
- app/(protected)/admin/ledger/entries/page.tsx 및 PaymentVerificationSection.tsx — 공통 상세 연결
- scripts/audit-purchase-settlement.mjs — 로컬 스냅샷 전용 읽기 감사/CSV 생성
- tests/purchase-settlement.test.mjs — 계산/격리 SQL/정밀도
- tests/purchase-settlement-concurrency.test.mjs — 로컬 전용 동시성·재시도·월마감 감사
- tests/purchase-settlement-browser.test.mjs — 실제 조회값 기반 다국어·반응형
- tests/ledger-payable-display.test.ts, tests/ledger-payable-payments.test.ts — 확장된 SELECT 구조 검사 갱신
