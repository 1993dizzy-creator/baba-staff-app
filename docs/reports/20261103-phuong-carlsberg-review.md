## 안전한 실행 순서

**지급 정정 → 정정된 상태의 새 보호 스냅샷·새 manifest 검토/승인 → 8월 재구축**을 권고한다. 이것은 실행 승인이 아니며, 현 REVIEW SQL은 기본값에서 중단한다.

1. 기존 302건·69,215,076의 배분 전체와 지급·매입·요청·감사 원본을 독립 스냅샷으로 보관한다. 영향 후보 19건·32,749,992 = #1641 12건·19,992,000 + #3337 6건·9,587,992 + #2399 1건·3,170,000. 이는 변경 허용 목록이 아니다.
2. 승인된 부분부터 별도 DB 승인으로 정정한다. Phase A만 적용하면 보호 집합은 **290건·49,223,076**이 된다. #3337의 6건과 #2399→#388은 이 단계에서 남는다. Carlsberg 해당 APP 미지급은 합계 19,992,000 증가하고 Phương 지급은 19,992,000 미배분으로 남는다. 이는 공급자 외부 청구잔액의 계산이 아니다.
3. 재구축의 `requiredProtectedFingerprints` 다섯 종류 전체를 정정 후 상태로 다시 수집하고, 새 manifest와 승인 digest를 검토한다. 배분과 추가 감사 행 때문에 기존 승인 snapshot은 재사용할 수 없다. 코드 계약 검증 PASS는 코드가 같으면 재사용한다. 기존 manifest·감사 근거를 덮어쓰지 않는다. 새 manifest 승인이 없으면 재구축을 중단한다.
4. 이후 재구축을 별도 승인으로 진행한다. 불확실한 배분은 그대로 보존하며, 나중에 확정된 정정은 재구축 복구 계약과 함께 별도로 계획해야 한다.

v3 SQL의 `payable_fingerprint()`는 allocation **ID·payable ID·payment ID·금액**을 포함한다. `apply_v1`은 독립 승인 지문/건수와 현재 값을 대조(`APPROVED_PROTECTION_SNAPSHOT_STALE`, `LATER_PAYABLES_CHANGED`)하고 실행 전후 지문도 보존한다. `reverse_v1`은 실행 당시 지문과 다르면 `SOURCE_PROTECTION_DRIFT`로 중단한다. 따라서 동시 배분 변경은 전후 불변식에 어긋나고, 재구축 후 정정은 기존 reverse를 막는다. 이 검사를 수정·우회하지 않는다. 후속 정정 뒤 복구가 필요하면 정확한 원래 allocation ID까지 복원하는 별도 보상 계획·승인이 먼저 필요하며, 이번 작업은 그런 실행 SQL을 만들지 않는다.

저장소 SQL은 `C:\workspace\BABA_2026-08_rebuild_atomic_LOCAL_ONLY_v3.patch`의 SQL과 줄바꿈을 정규화해 비교했고 동일했다. 패치를 재적용하지 않았다.
