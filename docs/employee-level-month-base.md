# 직원 레벨 기준월 리뉴얼 — 구현 메모 (Owner 검토 대기)

상태: 로컬 main 구현. 이번 수정에서 운영 DB 쓰기·Migration 적용·Push·배포를 하지 않음. 2026-11-10 읽기 전용 조회에서는 기존 월 기준 컬럼을 확인했으며, 배포 전 기존 v10/RPC 권한과 Migration 상태는 별도 확인한다.

## 정책

| 구분 | 규칙 |
|---|---|
| 입사월 기준(자동) `hire_month` | 입사일 1~15일: 입사월이 기준월. 16일~말일: 다음 달이 기준월(연도 이월 포함). **저장할 때 확정한 기준월을 버전에 보관**하고, 계산은 그 값을 쓴다(입사일 수정·재입사가 과거 이력을 바꾸지 않음). 입사일 수정으로 기준월이 달라지면 적용 월을 정해 새 버전으로 저장해야 한다(v10이 적용 월 없는 저장을 `LEVEL_BASE_MONTH_REVIEW_REQUIRED`로 거부) |
| 직접 기준월 `override_month` | 관리자가 `YYYY-MM`을 지정하고 자동 계산은 쓰지 않음. 실제 입사월 이전은 불가. 퇴사월 이후도 불가 |
| 공통 | 기준월 1일이 Lv.0. 승급은 기준월 +3·+6·+9개월…의 1일. 최대 Lv.7, 1회 500,000₫, 24개월 후 협의(★) 유지 |
| 기준월 이전 | 입사 후 기준월 시작 전(예: 16일 이후 입사자의 입사월)은 Lv.0으로 표시 |
| 과거 날짜 기준 `hire_date`/`override` | 과거 계산의 내부 호환만 유지. 일반 UI에서 날짜 기준을 선택·편집하지 않음. 모달은 월 기준 후보로 열리고 설정 반영 후 최종 저장할 때 신규 월 정책으로 전환. 기본정보만 저장·취소 시 정책 보존 |
| 급여 인상 반영 `salary_raise_enabled` | 레벨 ON과 별개. 기존 버전은 반영(true)으로 보존. **신규 직원·레벨 OFF→ON·레벨 ON 재입사는 반영 여부를 반드시 선택**(API·RPC 모두 `SALARY_RAISE_DECISION_REQUIRED`). 미반영이면 실제 급여 반영액 0₫. 시급제는 원래부터 레벨 인상 미반영. `users.part`·`pay_type`로 FT/PT를 판정하지 않음 |

- 레벨 계산 엔진(기준일 + 3개월 단위 기념일)은 바꾸지 않았다. 기준월을 그 달 1일로 넣어 같은 결과를 얻는다.
- 특별 인상(계약 `fixed_raise_amount`)과 정기 레벨 인상은 별도 항목이며, 중복으로 더하지 않는다.

## 과거 지급 보호

- 레거시 직원은 새 코드에서도 레벨 정보·보상 계산 결과·급여 해시가 바이트 단위로 같다. HEAD 코드와 42개 조합을 비교하는 테스트로 고정했다.
- 새 필드는 기본값일 때 아예 넣지 않는다. 급여 해시는 값이 없는 키를 건너뛰기 때문이다.
- `payroll_employee_payments`의 스냅샷·해시·금액·상태는 앱 코드와 Migration 모두 쓰지 않는다.
- 새 레벨 버전은 기존 규칙대로 이번 달·다음 달부터만 적용된다.

## 감사 후 남은 결정 사항

- **기존 `hire_date` 방식 버전의 위험(기존 동작, 이번 변경과 무관):** 이 방식은 계산할 때 현재 `users.hire_date`를 쓴다. 그래서 재입사나 입사일 수정이 있으면 과거 월 레벨이 다시 계산된다.
  - 예: 과거 9월 Lv.3 → 재입사 후 계산 불가.
  - 현재 운영 데이터는 모든 `hire_date` 버전의 `base_date`가 입사일과 같아서, 저장값을 쓰도록 바꿔도 결과가 같다.
  - 다만 과거 버전의 의미를 바꾸는 일이므로 Owner 결정이 필요하다.

## 앱·DB 호환성

- **Migration 전에 새 앱을 배포하면** 다음이 모두 실패한다.
  - 레벨 버전 조회(`salary_raise_enabled`): 직원관리, 근태 직원목록·프로필, 바, 급여 직원·계약, 월 급여 계산·개요
  - `users.level_base_mode` 조회: 위와 같은 화면
  - v10·v6·v4 호출: 직원 저장·생성·재입사
- **Migration 후 기존 앱(v9·v5·v3)은 레거시 직원에 대해 정상 동작한다**(PGlite로 실제 v9·v5·v3 정의를 실행해 확인). 월 모드 직원은 새 앱에서만 생기므로, 새 앱 배포 뒤에는 v9·v5·v3 회수를 권장한다.

## 운영 적용 순서 (각 단계 별도 승인)

1. **Migration을 먼저 적용한다.** 이 코드는 새 컬럼(`salary_raise_enabled`, `level_base_mode`)을 조회하므로, Migration보다 먼저 배포하면 직원·급여·근태·바 화면 조회가 실패한다.
2. DB 검증: 컬럼·제약·함수·권한을 확인하고 레거시 행이 그대로인지 확인한다.
3. 앱을 배포한다(v10·v6·v4 호출, v4는 `p_salary_raise_enabled` 인자 포함).
4. 시트 기준월로 기존 직원 버전을 정정한다. 운영 DB 쓰기이므로 별도 승인이 필요하다.

## 2026-11-10 월 기준 전환 수정 및 실행 계획

### UI와 저장 계약

- 모달은 두 모드만 제공한다. 기존 hire_date는 hire_month, override는 해당 기준월의 override_month를 기본 후보로 만든다. 적용월은 다음 달 권장이다.
- 후보의 레벨·승급일은 실제 월 기준 엔진으로 계산한다. 이전 정책과의 비교는 선택 적용일에 계산하며, 날짜 기준 편집 영역은 없다.
- 후보 생성·모달 취소는 사용자/버전/감사 로그를 쓰지 않는다. 설정 반영은 상세화면 draft만 바꾸며 최종 저장에서 기존 PATCH/v10으로 반영한다.
- 기본정보 저장은 현재 정책과 null effective_from을 전송한다. 예약된 다음 정책을 현재 월로 복사하지 않으며, 직급 수정도 임의로 레벨 ON/OFF를 변경하지 않는다.
- API는 새로운 날짜 기준 정책 변경을 LEVEL_MONTH_BASE_REQUIRED로 거부한다. 과거 날짜 정책의 무변경 저장은 허용한다.
- v10의 같은 적용월 덮어쓰기 동작으로 레거시 행 내용이 교체되지 않도록, 해당 월에 시작한 레거시 버전이 있으면 UI/API가 LEVEL_MONTH_TRANSITION_CONFLICT로 전환을 막는다.

### 전체 직원 사전 비교 (운영 쓰기 0건)

2026-11-10 읽기 전용 GET으로 사용자 29명, 레벨 버전 33개, 계약 25개를 조회했다. 기본 적용일은 2026-12-01이다. 모든 직원의 후보 및 검토 사유는 로컬 .local/level-month-transition-report.md와 .json에 보관한다. 원본 자료는 .local/level-month-transition-source.json이다. 개인별 급여 자료는 Git에 추가하지 않는다.

- 전환 후보 17명: 적용 여부·인상 반영 여부는 기존 값 유지. 이 중 OFF 6명은 전환해도 계속 OFF다.
- 검토/제외 12명: 퇴사/비활성, 시스템 계정, 입사일/계약 누락 등을 표시했다. 자동 실행 대상에 포함하지 않는다.
- Diep: 적용일 Lv.4 → Lv.4, 다음 승급일 2027-02-02 → 2027-02-01, 적용일 월급 환산 차이 0₫.
- Triem·Thành·Nhung: 적용일에 각각 1단계 차이, 월급 환산 정기 인상분 +500,000₫. 기존 승급일보다 월 1일 승급이 앞당겨지는 결과다. 실제 12월 지급 차이는 재직일·계약·일할 계산·마감 상태로 별도 확인한다.
- override 후보는 기존 기준월을 보존한다. 별도 시트의 다른 기준월로 임의 대체하지 않는다. 예: Linh H의 기본 후보는 2026-01이다.
- 특별 인상 fixed_raise_amount는 기존 보상 함수에서 한 번만 합산한다. 위 차이는 월급 계약 환산 비교이며 실지급액·순급여 차이가 아니다. 시급/일급의 정기 레벨 인상액은 기존대로 0₫다.

### Owner 승인 이후의 실행 순서 (이번 작업에서는 미실행)

1. 실행 직전에 대상 ID, 입사일, 버전 ID/revision, 적용월, 급여 계약을 다시 읽어 승인한 비교표와 일치하는지 확인한다. 예약 정책·변경된 revision·퇴사/시스템 계정은 자동 진행하지 않는다.
2. 승인 범위는 직원 ID별 후보 모드·기준월·적용월·ON/OFF·급여 반영 여부로 확정한다. 기본 적용일은 2026-12-01이며, 실행일이 달라지면 비교표부터 갱신한다.
3. v10을 직원별로 호출한다. hire_date/계약/특별 인상/기존 감사 로그/지급 데이터는 변경하지 않는다. 해당 적용월에 기존 레거시 버전이 있으면 덮어쓰지 않고 별도 일정 검토로 돌린다. 운영 일괄 실행 스크립트는 만들거나 실행하지 않았다.
4. v10은 신규 버전을 추가하면서 활성 이전 버전의 effective_to만 새 적용일로 종료한다. 기존 기준·모드·revision·감사 로그 내용은 보존한다. **기존 행의 effective_to까지 완전히 불변이어야 한다는 뜻이라면 v10은 그대로 재사용할 수 없다. 이 구간 종료 변경은 Owner의 운영 승인 범위에 반드시 포함해야 하며, 엄격한 전체 행 불변이 필요하면 별도 저장 계약 검토가 필요하다.**
5. 신규 버전의 mode/base_date(월 1일)/enabled/salary_raise_enabled 및 감사 로그의 이전/다음 스냅샷을 대조한다. 적용일 전 날짜의 버전 선택·계산과 지급 snapshot/hash/금액/상태가 보존되는지 확인한다. 새로운 버전은 다음 달 정책이므로 현재 월은 다시 계산하지 않는다.

이번 수정에 신규 Migration은 필요하지 않다. 기존 20261110030000_employee_level_month_base_v1.sql/v10을 전제로 한다. 과거 레거시 계산 엔진·근태 재직기간 판정·급여 해시/스냅샷 구조는 변경하지 않았다.

API의 동일 월 보호 검사는 읽은 버전 기준이며 v10에 예상 revision 인자는 없다. 조회와 RPC 사이 다른 관리자의 정책 저장까지 원자적으로 차단하는 계약은 아니므로 운영 전환은 직원별 직렬 처리하고 동시 정책 편집을 피해야 한다. 전체 행 불변 또는 원자적 revision 검사가 필요하면 별도 DB 계약 변경을 검토한다.
